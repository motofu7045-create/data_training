# git の使い方

このリポジトリを自分の Mac で実際に操作しながら学ぶ。

## 全体像

ファイルの変更は4つの場所を順に移っていく。

```
作業フォルダ  →  ステージ  →  ローカルの履歴  →  GitHub（リモート）
（編集する）   git add      git commit         git push
                                   ←──────────────── git pull
```

| コマンド | 意味 |
| --- | --- |
| `git add` | この変更を次の記録に入れると選ぶ |
| `git commit` | 選んだ変更を、メッセージ付きで自分の PC の履歴に記録する |
| `git push` | 自分の PC の履歴を GitHub に送る |
| `git fetch` | GitHub の最新の履歴を取ってくるだけ（手元のファイルは変わらない） |
| `git pull` | fetch ＋ 取り込み（merge）をまとめて行う |

## 状態を確認するコマンド

| コマンド | 何が分かるか |
| --- | --- |
| `pwd` | 今いるフォルダの場所 |
| `git remote -v` | このフォルダがどの GitHub リポジトリとつながっているか |
| `git branch` | 今いるブランチ（`*` が付いているのが今のブランチ） |
| `git status` | 手元に未保存の変更があるか、GitHub と比べて遅れているか |
| `git log --oneline -5` | 直近5件の記録（コミット） |

## 学んだこと

### `git status` の「up to date（最新）」は古い情報のことがある

- `origin/main` は「GitHub の main を**最後に確認したとき**の記録」にすぎない
- **Git は自分から GitHub を見に行かない**。`git fetch` するまで、手元の `origin/main` は古いまま
- 本当に最新かを知るには、先に `git fetch` してから `git status` を見る

### 接続方法: SSH

- `git remote -v` で `git@github.com:...` と出たら **SSH** で GitHub とつながっている
- SSH の鍵が使えないと、fetch・pull・push のときに `Permission denied (publickey)` が出る → [01_ssh_key_setup.md](01_ssh_key_setup.md)

### ページャー（less）から抜けるには `q`

`git log` などの結果が長いと、閲覧モード（ページャー）で表示される。文字を打ってもコマンドにならない。

| キー | 動作 |
| --- | --- |
| `q` | **終了する** |
| `↓` / `↑` | 1行ずつ移動 |
| スペース / `b` | 1画面ずつ移動 |
| `/文字` + Enter | 検索（`n` で次） |

ページャーを使わずに表示したいときは `git --no-pager log ...`。

### add・commit・push の役割（よくある勘違い）

| | 勘違い | 正しくは |
| --- | --- | --- |
| add | － | 次の commit に入れる変更を**ステージ（カゴ）**に乗せる |
| commit | ステージング環境に上げる | ステージの変更を**自分の PC の履歴に記録**する |
| push | 本線に合流する | 自分の PC の履歴を **GitHub の同じ名前のブランチに送る**だけ。本線（main）に合流させるのは **merge**（プルリクエスト） |

- 買い物にたとえると: add ＝ カゴに入れる、commit ＝ 会計してレシートをもらう（手元だけ）、push ＝ レシートを本社に送る
- 「ステージング環境」は本番前のテスト用サーバーのこと。Git のほうは「**ステージングエリア**」

### commit の価値

| | 保存（⌘S） | commit |
| --- | --- | --- |
| 残るもの | 最新の状態だけ（上書き） | その時点の状態が全部残る（**セーブポイント**） |
| 戻れるか | 戻れない | いつのセーブポイントにも戻れる |
| 理由 | 残らない | 「なぜ変えたか」をメッセージで残せる |

- 実例: 比較表のデータローダの上限を直した記録が残っている
  - `git log --oneline -- docs/salesforce_admin/comparison.md`（このファイルを変えた commit の一覧）
  - `git show a8bace2 -- docs/salesforce_admin/comparison.md`（`-` が消えた行、`+` が追加した行）
- 実務では: ETL を直したら翌朝データがおかしい → どの commit が原因かを特定して、その commit だけ取り消せる（`git revert`）
- commit は自分用、push はみんなへの共有。作業中はこまめに commit し、まとまったら push する

### add と commit を分ける意味

- add は何回やっても**同じ1つのカゴ**に入る。commit するとカゴの中身が**全部まとめて**1つの commit になる
- add は「**その瞬間のファイルの中身**」を撮ってカゴに入れる。add のあとに編集した分は、もう一度 add しないと入らない（`git status` で同じファイルが2回出る）
- カゴから出す: `git restore --staged ファイル名`（ファイルの中身は消えない）

| コマンド | 何を見るか |
| --- | --- |
| `git diff` | カゴに**入っていない**変更 |
| `git diff --staged` | カゴに**入っている**変更（次に commit される内容） |

**分けなくていいとき**: 変更を全部まとめて1つの commit にしてよいなら、`git diff` で確認して `git commit -am "メッセージ"` で十分。ただし新しく作ったファイルは対象外で、`git diff` にも出ない（`git status` の Untracked files で確認する）。

**add がないとできないこと**: 変更の**一部だけ**を記録すること。同じファイルの中でも、`git add -p` で一部の行だけを選べる。
例: ETL のスクリプトで、10行目のバグ修正はすぐ commit したいが、50行目の新機能はまだ途中 → 10行目だけをカゴに入れて commit する。

### 入れてはいけないものを入れない

パスワードや AWS のアクセスキーを書いたファイル（`.env` など）を commit して push する事故はよくある。**一度 commit すると履歴に残る**ので、後でファイルを消しても過去の commit から見えてしまう。

- commit する前に `git diff --staged`（または `git diff` と `git status`）で確認する
- 中身を見ずに `git add .` や `git commit -a` をしない
- パスワードなどのファイルは `.gitignore` に書いて、Git の管理対象から外す
