## 1-3. ユーザー管理

### ユーザーの基本

| 項目 | ポイント |
| --- | --- |
| ユーザー名 | **メールアドレス形式**。**Salesforce 全体で一意**（実在のメールアドレスでなくてよい） |
| メールアドレス | 組織間で同じでもよい |
| ユーザーライセンス | 使える機能が決まる。**選べるプロファイルもライセンスで決まる** |
| プロファイル | 1ユーザーに**1つだけ** |
| ロール | 任意 |
| 別名 | 名前が入りきらないときの短縮名（デフォルトは名の1文字目＋姓の4文字） |

- ユーザーの追加: 1人ずつ、または [複数のユーザーを追加] で**最大10人**まで一度に
- 初回ログイン時にパスワードの変更が必要。ログインリンクは**1回だけ**使える
- 地域の設定（言語、タイムゾーン、ロケール）はユーザーごとに設定できる
- 他のユーザーとしてログインする: システム権限が有効か、ユーザーがシステム管理者のログインアクセスを許可している必要がある

### 凍結 と 無効化（試験に出やすい）

| | 凍結 | 無効化 |
| --- | --- | --- |
| ログイン | できなくなる | できなくなる |
| **ライセンス** | **空かない** | **空く**（他のユーザーに使える） |
| 使う場面 | アカウントが不正アクセスされた疑い。**すぐに無効化できないとき**（カスタム階層項目で選ばれているなど）の一時対応 | 退職したとき |

- ユーザーは**削除できない**（レコードが孤立するのを防ぐため）。代わりに無効化する
- 無効化されたユーザーはすべてのレコードにアクセスできなくなるが、データは残る（他のユーザーに移せる）
- **ユーザーアクセスの概要**: ユーザーの詳細ページで、そのユーザーの権限や、どの公開グループ・キューに入っているかを確認できる

出典: [新規ユーザーの追加](https://trailhead.salesforce.com/ja/content/learn/modules/lex_implementation_user_setup_mgmt/lex_implementation_user_setup_mgmt_adding_users-hoc)、[組織へのアクセスの制御](https://trailhead.salesforce.com/ja/content/learn/modules/data_security/data_security_org)

## 1-4. データアクセスの4つのレベル

| レベル | 何を制御するか | 主な機能 |
| --- | --- | --- |
| **組織** | 誰がいつどこからログインできるか | パスワードポリシー、ログインIPアドレスの制限、ログイン時間帯の制限 |
| **オブジェクト** | オブジェクトのレコードを作成・参照・編集・削除できるか | プロファイル、権限セット、権限セットグループ |
| **項目** | 特定の項目を参照・編集できるか | 項目レベルセキュリティ（プロファイル、権限セット） |
| **レコード** | どのレコードが見えるか | 組織の共有設定、ロール階層、共有ルール、手動共有 |

- セキュリティ設定は **API でデータを扱うときにも適用される**
- 設計のコツ: ユーザーの種類ごとに「どのオブジェクト・項目・レコードにどのアクセスが必要か」を表にまとめてから設定する

出典: [データセキュリティの概要](https://trailhead.salesforce.com/ja/content/learn/modules/data_security/data_security_overview)

## 1-5. 組織レベル（ログインの制御）

| 機能 | 何ができるか | 設定する場所 |
| --- | --- | --- |
| パスワードポリシー | 長さ、複雑さ、有効期間、ロックアウトまでの失敗回数 | [設定] → 「パスワードポリシー」。**プロファイルでも設定でき、プロファイルの設定が組織の設定より優先される** |
| **ネットワークアクセス**（信頼済みIP範囲） | この範囲からのログインは**確認コードが不要**になる | [設定] → 「ネットワークアクセス」 |
| **プロファイルのログインIPアドレスの制限** | この範囲の**外からはログインできない** | プロファイル → 「ログイン IP アドレスの制限」 |
| ログイン時間帯の制限 | プロファイルごとにログインできる曜日・時間帯を決める | プロファイル → 「ログイン時間帯の制限」 |

**ネットワークアクセス と プロファイルのIP制限 の違い（試験に出やすい）**

- ネットワークアクセス: 範囲外でも**ログインはできる**（確認コードを入力すればよい）
- プロファイルのIP制限: 範囲外からは**ログインできない**

その他:
- デフォルトでは、どのIPアドレスからでもログインできる
- ログイン時間帯が終わると、表示中のページは見られるが**操作はできなくなる**
- 特定の曜日を使えなくするには、開始時刻と終了時刻を同じにする

出典: [組織へのアクセスの制御](https://trailhead.salesforce.com/ja/content/learn/modules/data_security/data_security_org)

## 1-6. オブジェクトと項目のレベル

### プロファイル・権限セット・権限セットグループ（試験に出やすい）

| | プロファイル | 権限セット | 権限セットグループ |
| --- | --- | --- | --- |
| 1ユーザーにいくつ | **1つだけ** | 複数 | 複数 |
| 役割 | **デフォルト設定** | **権限を追加**する（タスク単位） | 権限セットを**職務（ペルソナ）単位でまとめる** |
| ここで設定するもの | **デフォルトのアプリケーション、デフォルトのレコードタイプ、ページレイアウトの割り当て、ログインIP範囲、ログイン時間帯** | オブジェクト権限、項目権限、ユーザー権限（アプリケーション権限・システム権限）、タブの設定、Apex クラス、Visualforce ページ、接続アプリケーション、カスタム権限 | 権限セットの組み合わせ |

- **推奨の考え方**: プロファイルは「**最小アクセス - Salesforce**」にして、必要な権限は権限セットと権限セットグループで足す
- **標準プロファイルのオブジェクト権限は編集できない**。コピーしてカスタムプロファイルを作る
- システム管理者プロファイルの「**すべてのデータの参照**」「**すべてのデータの編集**」は**すべての共有設定より優先**される。他のプロファイルに付けるときは注意
- 権限を取り消すには、プロファイルと**すべての**権限セットから外す必要がある
- 権限セットグループの割り当てには**有効期限**を付けられる（一時的な割り当てに便利）
- ライセンスで許可されない権限を含む権限セット（グループ）は、そのユーザーに割り当てられない
- 確認に使える画面: オブジェクトマネージャーの「オブジェクトアクセス」、ユーザーの「概要を表示」、権限セット（グループ）の「概要を表示」

### ミュート権限セット

- 権限セットグループの中の**特定の権限だけを無効にする**
- 権限セットグループごとに**1つ**
- 影響するのは**そのグループに割り当てられたユーザーだけ**。同じ権限をプロファイルや別の権限セットから得ていれば、そのユーザーは使える
- 連動する権限もミュートされる（例: 「参照」をミュートすると「作成」「編集」「削除」なども使えなくなる）

### 権限セットグループの再適用

- 中の権限セットを変更・追加・削除すると**再適用**が始まる
- 再適用中、ユーザーは**前回完了した時点の権限**のまま
- 状況: 更新／期限切れ／更新中／失敗

### 項目レベルセキュリティ

- 項目ごとに「参照」「編集」を制御する
- **ページレイアウトと違い、関連リスト・リストビュー・レポート・検索結果など、すべての場所に効く**。項目を確実に見せたくないときは項目レベルセキュリティを使う
- 設定する場所: プロファイル、権限セット、[設定] → 「項目アクセス許可」、またはオブジェクトマネージャーの項目 → 「項目レベルセキュリティの設定」（複数の権限セットをまとめて設定できる）

出典: [オブジェクトへのアクセスの制御](https://trailhead.salesforce.com/ja/content/learn/modules/data_security/data_security_objects)、[項目へのアクセスの制御](https://trailhead.salesforce.com/ja/content/learn/modules/data_security/data_security_fields)、[権限セットグループ](https://trailhead.salesforce.com/ja/content/learn/modules/permission-set-groups)

## 1-7. レコードのレベル（共有）

### 4つの仕組み（下に行くほどアクセスが広がる）

1. **組織の共有設定**: 自分が所有していないレコードへの**基本のアクセス**。一番厳しいユーザーに合わせて設定する
2. **ロール階層**: 上位のロールは、**下位のユーザーが所有・共有されているレコード**を参照・編集・レポートできる（**縦**の共有）
3. **共有ルール**: 特定のグループに自動でアクセスを広げる（**横**の共有）
4. **手動共有**: レコードの所有者などが、個別のレコードを他のユーザーと共有する

- これらは**アクセスを広げるだけ**。組織の共有設定より**狭くすることはできない**
- 組織の共有設定は、**オブジェクト権限を超えるアクセスは与えられない**

### 組織の共有設定の選択肢

| 設定 | 他人のレコードを | 使う場面 |
| --- | --- | --- |
| 非公開 | 見られない（所有者と上位ロールだけ） | 参照させたくないレコードがある |
| 公開/参照のみ | 見られるが編集できない | 編集させたくないレコードがある |
| 公開/参照・更新可能 | 見られて編集もできる | 制限が不要 |
| 親レコードに連動 | 親レコードと同じ | 主従関係の従オブジェクト（**親の設定を自動で引き継ぐ**） |

決め方（オブジェクトごとに考える）:
1. 一番制限されるユーザーは誰か
2. その人に**参照**させたくないレコードはあるか → あれば「非公開」
3. その人に**編集**させたくないレコードはあるか → あれば「公開/参照のみ」

その他:
- 内部ユーザーと外部ユーザーで別々に設定できる
- カスタムオブジェクトは「**階層を使用したアクセス許可**」をオフにすると、ロール階層による自動アクセスを止められる（標準オブジェクトは止められない）
- 変更すると**共有の再適用**が自動で行われ、終わるとメールが届く
- 設定する場所: [設定] → 「共有設定」

### ロール階層

- **組織図と一致させる必要はない**。各ロールは「必要なデータアクセスのレベル」を表す
- 例: 正社員と準社員のエンジニアを1つのロールにまとめてよい
- 設定する場所: [設定] → 「ロール」

### 共有ルール

3つの要素で作る: **どのレコードを**（所有者に基づく／条件に基づく）、**誰と**（ロール、ロールと下位ロール、テリトリー、公開グループ）、**どのアクセスで**（参照のみ／参照・更新）

- **予測できる決まったグループ**に向いている（例: 採用担当者全員）
- **誰が対象になるか予測しにくい**場合（例: 案件ごとに変わる面接官）は向かない → 手動共有などを使う
- 公開グループ: ユーザー、ロール、ロールと下位ロール、テリトリー、他の公開グループの組み合わせ。共有の対象が1〜2グループを超えるなら公開グループを作ると管理しやすい

### 取引先チーム

- 取引先ごとに、一緒に担当するメンバーと役割（例: 営業担当技術者、カスタマーサポート担当）を登録する
- メンバーごとに、取引先・商談・ケースへのアクセス権（参照のみ／参照・更新）を付けられる
- **デフォルトの取引先チーム**を作っておくと、取引先に追加しやすい

出典: [レコードへのアクセスの制御](https://trailhead.salesforce.com/ja/content/learn/modules/data_security/data_security_records)、[ロール階層の作成](https://trailhead.salesforce.com/ja/content/learn/modules/data_security/data_security_roles)、[共有ルールの定義](https://trailhead.salesforce.com/ja/content/learn/modules/data_security/data_security_sharing_rules)、[取引先チームの設定](https://trailhead.salesforce.com/ja/content/learn/projects/protect-your-data-in-salesforce/set-up-account-teams)

## 1-9. ID とログインの仕組み（Salesforce Identity）

| 機能 | 何ができるか |
| --- | --- |
| **シングルサインオン（SSO）** | 1回のログインで、他のアプリにもログインし直さずに入れる |
| **ソーシャルサインオン** | Google、Facebook、LinkedIn などのアカウントでログインする。顧客向けの Experience Cloud サイトで特に便利 |
| **多要素認証（MFA）** | パスワードに加えて、認証アプリやセキュリティキーなど**2つ以上の要素**でログインする。**Salesforce に直接ログインする全ユーザーに必須** |
| 私のドメイン | ログインURLに会社名を入れる（例: `https://会社名.my.salesforce.com`） |
| アプリケーションランチャー | 組織内のアプリや外部アプリをタイルで一覧表示する |
| 外部クライアントアプリケーション | 外部アプリを Salesforce と連携させる |

### プロトコル

| プロトコル | 何に使うか |
| --- | --- |
| **SAML** | **SSO** を実現する。XML ベース |
| **OAuth 2.0** | アプリ間で安全に**データを共有**する（例: モバイルアプリから Salesforce のデータを表示） |
| **OpenID Connect** | OAuth 2.0 に認証を加えたもの。**ソーシャルサインオン**に使う |

### ID プロバイダー と サービスプロバイダー

- **ID プロバイダー（IdP）**: ユーザーを**認証する**側
- **サービスプロバイダー（SP）**: 認証された ID を**受け入れる**側（アプリ）
- Salesforce はどちらにもなれる（例: Salesforce から Gmail に入るなら、Salesforce が IdP、Google が SP）

用語:
- **認証**: 「誰であるか」を確認する
- **承認**: 「特定の権限を持っているか」を確認する
