## 7-1. 自動化の種類

まず「**ユーザーの入力が必要か**」で分ける。

### ユーザーの入力が必要（インタラクティブ）

| 機能 | 内容 |
| --- | --- |
| **画面フロー** | 画面で情報を見せたり、ユーザーに質問したりする |
| 自動起動フロー | ボタンのクリックなどで実行する。他の自動化から呼び出すこともできる |
| **承認プロセス** | 承認者を割り当てた一連のステップ。レコードのロックや更新も自動化できる |
| Lightning Web コンポーネント | HTML と JavaScript のコードで作る |
| Visualforce | HTML と Apex のコードで作るページ |

### バックグラウンドで自動実行

| 機能 | いつ実行されるか |
| --- | --- |
| **レコードトリガーフロー** | レコードが**作成・更新・削除**されたとき |
| **スケジュールトリガーフロー** | **指定した日時・頻度**で |
| プラットフォームイベントトリガーフロー | プラットフォームイベントのメッセージを受け取ったとき |
| Data 360 トリガーフロー | Data 360 のデータが変わったとき |
| Apex | コードで書く。さまざまな方法で起動できる |

### フローか、コードか

- **まず宣言型ツール（フロー）を検討し、できなければコード**を考える。フローの方が作るのも保守するのも簡単
- フローでできないこともある（例: PDF の生成）。その部分だけコードで作り、フローから呼び出す組み合わせもできる

### ツール選びの例

「取引先責任者を作る前に重複を確認し、あれば更新、なければ作成。最後に Chatter に投稿する」

| ツール | フォーム | 条件分岐とアクション | コード |
| --- | --- | --- | --- |
| クイックアクション | ○ | **×** | 不要 |
| **フロー** | ○ | **○** | **不要** |
| Lightning コンポーネント | ○ | ○ | **必要** |

→ 条件分岐が必要でコードは避けたいので、**フロー**を選ぶ。

> 補足（[比較表](../comparison.md) より）: ワークフロールールとプロセスビルダーは廃止に向かっていて、新しくは作れない。今の試験では、自動化の答えは基本的にフロー。

出典: [ビジネスプロセスの自動化入門](https://trailhead.salesforce.com/ja/content/learn/modules/flow-basics/get-started-with-flows)、[フローを活用する](https://trailhead.salesforce.com/ja/content/learn/modules/flow-basics/go-with-the-flow-th)

## 7-2. フローの部品（Flow Builder）

フローは **要素・コネクタ・リソース** の3つでできている。

| 部品 | 内容 |
| --- | --- |
| **要素** | フローの各ステップ（キャンバスに表示される） |
| **コネクタ** | 要素どうしをつなぐ線。次にどの要素を実行するかを決める |
| **リソース** | 要素から参照する値の入れ物（キャンバスには表示されない） |

### 要素の3つの種類（試験に出やすい）

| 種類 | 何と対話するか | 主な要素 |
| --- | --- | --- |
| **インタラクション** | **ユーザー** | **画面**（表示・入力）、**アクション**（Chatter 投稿、メール送信、**承認申請**、モバイル通知、送信メッセージ）、**サブフロー**（他のフローを呼び出す） |
| **データ** | **Salesforce のレコード** | **レコードを取得・作成・更新・削除**（1件ずつでも複数件まとめてでも） |
| **ロジック** | **フロー自体** | **決定**（条件で分岐）、**割り当て**（一時データを更新）、**ループ**（データの集まりを1件ずつ処理）、**一時停止**（指定時刻まで待つ）、コレクションの並び替えなど |

- ロジック要素で変えたデータは**フローの実行中だけ**有効。フローの外に残すには、データ要素（レコードの作成・更新）や外部へのアクションを使う

### リソースの種類

| リソース | 内容 |
| --- | --- |
| **変数** | 値を入れておく容器。フローの中で値が変わる。データ型: テキスト、数値、Boolean（**True / False のグローバル定数**を使う）、日付・日時、**レコード**（レコードのすべての値をまとめて持つ） |
| **定数** | 値が変わらない（例: pi = 3.14159） |
| **数式** | 数式項目とほぼ同じ。**参照されるたびに再計算**される |
| テキストテンプレート | 書式付きの長いテキスト |

- フローが実行されるたびに、変数は**デフォルト値から始まる**（前回の値は引き継がれない）
- 多くの要素は自分で出力用の変数を作ってくれる

### その他

- レコードトリガーフローでは、**テスト**（期待どおりに動くかのシナリオ）を作れる
- ボタンバーに **[実行]** と **[デバッグ]** がある

出典: [Flow Builder の概要](https://trailhead.salesforce.com/ja/content/learn/modules/flow-basics/meet-flow-builder)、[フロー変数](https://trailhead.salesforce.com/ja/content/learn/modules/flow-basics/learn-about-flow-variables)

## 7-3. 画面フローの例（重複チェック付きの取引先責任者作成）

| やりたいこと | 要素 |
| --- | --- |
| 名前・取引先・メールを入力してもらう | **画面**（名前、**選択肢ルックアップ**、メールのコンポーネント） |
| 同じメールの取引先責任者を探す | **レコードを取得** |
| 見つかったかで分岐する | **決定** |
| 見つかったら、更新するかユーザーに聞く | 画面（切り替えコンポーネント）＋決定 |
| 既存を更新する | **割り当て**（レコード変数に ID を入れる）→ **レコードを更新** |
| 新規に作る | **レコードを作成** |
| 結果を伝える | 画面 |

- **レコード変数**を1つ用意し、すべての値をまとめて持たせると、作成・更新が楽になる

出典: [重複がないかチェックする画面フローを作成する](https://trailhead.salesforce.com/ja/content/learn/projects/build-a-simple-flow)

## 7-4. 承認プロセス（試験に出やすい）

**承認プロセス**: レコードの承認を自動化する。**承認ステップと承認者**、**各段階で実行するアクション**を決める。

### 流れとアクション

| タイミング | アクション | 例 |
| --- | --- | --- |
| **申請時のアクション** | 申請されたとき | **デフォルトでレコードをロック**（承認者とシステム管理者以外は編集できない）、状況を「保留中」に |
| **承認ステップ** | ステップごとに承認者を割り当てる | 1つ目: 直属のマネージャー、2つ目: CEO |
| ステップの承認・却下時のアクション | 各ステップで | |
| **最終承認時のアクション** | **すべての承認が済み、次のステップがない**とき | 状況を「承認済み」に、申請者にメール |
| **最終却下時のアクション** | 却下されたとき | 状況を「却下」に、申請者にメール、ロック解除 |

教材で使っていたアクション: **項目自動更新**、**メールアラート**

### 設定の主な項目

| 設定 | 内容 |
| --- | --- |
| **開始条件** | どのレコードを承認プロセスに入れるか（例: 割引率 > 0） |
| 承認者の決め方 | **ユーザー項目**（例: **マネージャー**項目）で自動決定、申請者が手動で選ぶ、特定のユーザーやキューに自動割り当て |
| ステップの条件 | ステップごとに条件を付けられる（例: 15%超はマネージャー、40%超は副社長） |
| 編集権限 | 承認中に誰がレコードを編集できるか（例: 管理者のみ） |
| 複数の承認者 | 例: **最初の応答**に基づいて承認・却下する |
| 代理承認者 | 代理承認者も承認できるようにするか |
| 許可される申請者 | 例: レコードの所有者。**申請者に取り消しを許可**するか |
| 承認ページ | 承認者に見せる項目、承認履歴 |

### 使えるようにするまで

1. 必要な項目を作る（例: 割引率、承認状況の選択リスト）
2. **メールテンプレート**を作る（例: 承認依頼、承認通知、却下通知）
3. 承認プロセスを作り、**有効化**する
4. ページレイアウト（または Lightning ページの動的アクション）に「**承認申請**」ボタンを置く

その他:
- 申請を忘れないように、**フローのアクション要素で自動的に承認申請**することもできる
- ホームページに「**未承認申請**」コンポーネントを置くと、承認待ちが一目でわかる
- メールや Chatter から直接承認できるようにもできる（Chatter での承認は [5. 生産性](05_productivity.md) を参照）

出典: [承認プロセス](https://trailhead.salesforce.com/ja/content/learn/modules/business_process_automation/approvals)、[承認プロセスを作成する](https://trailhead.salesforce.com/ja/content/learn/modules/business_process_automation/build-an-approval-process)、[割引承認プロセスの作成](https://trailhead.salesforce.com/ja/content/learn/projects/build-a-discount-approval-process)
